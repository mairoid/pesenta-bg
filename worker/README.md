# pesenta-nap — Worker за е-бележката и одиторския файл

Сайтът остава статичен на GitHub Pages. Тук живее само това, което не може да
се случи в браузъра: приемането на Stripe webhook-а, регистрирането на
продажбата по чл. 52о и генерирането на месечния XML по Приложение №38.

**Защо изобщо съществува:** статична страница не може да разбере, че някой е
платил. Без този Worker всяко плащане остава само в Stripe и няма от какво да
се произведе одиторският файл.

---

## Първоначална настройка (веднъж)

Всички команди се пускат от папка `worker/`.

### 1. Схемата в базата

```bash
npx wrangler d1 execute pesenta-nap --remote --file=schema.sql
```

⚠️ **`--remote` е задължителен.** Без него wrangler пише в локална симулация и
всичко изглежда успешно, докато истинската база остава празна.

### 2. Тайните

Задават се от теб — не влизат в кода и не се виждат от никого, включително
от Claude. Всяка команда пита за стойността интерактивно:

```bash
npx wrangler secret put STRIPE_WEBHOOK_SECRET
```

```bash
npx wrangler secret put AUDIT_TOKEN
```

- `STRIPE_WEBHOOK_SECRET` — идва от Stripe при създаването на webhook-а (стъпка 4),
  започва с `whsec_`. С него Worker-ът проверява, че заявката наистина е от
  Stripe, а не подхвърлена измислена продажба.
- `AUDIT_TOKEN` — измисляш го ти, дълъг случаен низ. Пази одиторския файл от
  публичен достъп. Пази го, ще ти трябва всеки месец.

### 3. Публикуване

```bash
npx wrangler deploy
```

Отпечатва адреса — нещо от вида `https://pesenta-nap.<твой-subdomain>.workers.dev`.
Запиши го, трябва за следващата стъпка.

### 4. Webhook в Stripe

Stripe Dashboard → Developers → Webhooks → **Add endpoint**

- **URL:** `https://pesenta-nap.<твой-subdomain>.workers.dev/stripe-webhook`
- **Събития:** `checkout.session.completed` и `charge.refunded`

След създаването Stripe показва **Signing secret** (`whsec_…`) — това е
стойността за `STRIPE_WEBHOOK_SECRET` от стъпка 2.

### 5. Проверка

```bash
curl https://pesenta-nap.<твой-subdomain>.workers.dev/health
```

Трябва да върне `{"ok":true,"shop":"RF0007086"}`.

## Месечна рутина (1–15 число, за предходния месец)

```bash
curl -o audit.xml "https://pesenta-nap.<subdomain>.workers.dev/audit/2026-08?token=ТВОЯТ_AUDIT_TOKEN"
```

Файлът излиза в `windows-1251`, точно както го иска схемата на НАП. Подава се
през портала на НАП с КЕП. **Първото подаване е за август 2026, в прозореца
01–15.09.2026.**

Ако месецът няма нито една продажба, ендпойнтът връща 409 с обяснение вместо
файл — схемата на НАП изисква поне една поръчка и празен файл е невъзможен.

## Номерация на документите

Един брояч за всичко: номерът на е-бележката по чл. 52о и номерът на фактурата
са един и същ номер. Първият издаден е **0000001012**, следващият 0000001013 и
така нататък.

Броячът стои в таблица `counters`, не се смята като `MAX(doc_n)+1` — при две
едновременни плащания това би дало един и същи номер два пъти.

⚠️ **Провери, че счетоводната програма на „БАУФИЗИК" няма да стигне до 1012** по
своята последователност. Двете номерации не бива да се застъпват.

Ако някога трябва да се смени началото (само преди първата издадена фактура):

```bash
npx wrangler d1 execute pesenta-nap --remote --command "UPDATE counters SET value = 1011 WHERE name='doc_n'"
```

Стойността е с едно по-малка от първия желан номер.

## Какво е готово и какво не

**Готово и проверено:**
- Приемане на Stripe webhook с проверка на подписа (HMAC-SHA256) и защита
  срещу повторно пускане на стар подпис.
- Идемпотентност — Stripe ретрайва при неуспех; повторният webhook не издава
  втори документ.
- Запис на продажбите и възстановяванията в D1 (регион EEUR, данните остават в ЕС).
- Генератор на одиторския XML. **Валидиран срещу официалната XSD на НАП с 0
  грешки** в три сценария: продажби с възстановяване, продажби без
  възстановяване, и експресна поръчка с промо отстъпка.
- Сумите се държат в стотинки (цели числа) — никакъв float, за да се връзва
  аритметиката в одиторския файл.

**Още не е направено:**
- **Самата е-бележка** — документът, който се изпраща на клиента, с реквизитите
  по чл. 52о, ал. 1 и **QR кода по Приложение №18а**. Продажбата вече се
  записва коректно, но клиентът още не получава документ.
- Изпращането ѝ по имейл (иска външен доставчик, напр. Resend — Cloudflare
  Email Routing само получава, не праща до произволни адреси).
- Фактурата като отделен документ за сваляне.

**Затова `payments.js` остава на `enabled: false`.** Плащанията не бива да се
пускат, преди е-бележката да работи.
